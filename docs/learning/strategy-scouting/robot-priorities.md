## Overview

A robot that “does everything” does nothing well in week 6. Priorities are
how strategy becomes a build plan: must, should, and won’t. This lesson is
how to write that list so CAD and mechanical can say no to good ideas.

## Prerequisites

- [Scoring, Cycles & Penalties](../scoring-and-cycles/)
- The [Decision-Making Guide]({{ '/decision-making/' | relative_url }})

## What you'll learn

- How to write a must / should / won’t list.
- How to pick an alliance role, not just a mechanism list.
- How to change the list when prototypes fail.

## Unit 1 — Must / should / won’t

- **Must** — if this is missing, the robot cannot play the strategy. Keep
  the list short. Drivetrain, one scoring path, and a legal bumper set are
  typical musts; a third mechanism is not.
- **Should** — high value if the musts are already reliable.
- **Won’t** — good ideas you are not building this year. Writing them down
  is the point. It stops the same argument every Tuesday.

## Unit 2 — Role, not features

Ask what this robot is on an alliance:

- Primary scorer, complementary scorer, defender, or endgame specialist.
- What you need a partner to do because you will not.

A feature list without a role produces a robot that is busy and lonely.

## Unit 3 — Close the decision

- Prototypes and cycle math beat opinions. See Phase 3 of the
  [roadmap]({{ '/roadmap/' | relative_url }}).
- When people disagree, use the formal process. Do not relitigate a closed
  won’t list in the shop.
- Revisit the list after the first real test, not after every Slack
  message.

## Steps & acceptance criteria

- [ ] Write a must / should / won’t list with no more than four musts.
- [ ] State the alliance role in one sentence.
- [ ] Name one popular idea in won’t and the reason it is there.
- [ ] Walk the list with a CAD or mechanical lead and record their
      feasibility notes.
